# BOSS's own charge generation returns +1.00000 for any requested negative net charge

Requesting a negative net charge for any anion — a bare hydroxide, acetate, or a bistriflimide-sized species were all tested — makes `LigParGen.Converter.convert()` fail at `assert (mol.MolData['TotalQ']['Reference-Solute'] == charge)`. This traces back to old, unresolved reports on the original LigParGen issue tracker (`leelasd/ligpargen` #73, #79, and others) going back years.

Confirmed directly, not guessed: BOSS's own `/tmp/out` "Net Charge" section reports `1.00000` for every one of these anions regardless of the actual requested value or the input structure, even though `AM1SP-par` — the parameter file LigParGen hands to BOSS's `AM1SP-cmd` via the `xZCM1A-` script — is correctly populated with `AM1SCM1A 1.00 -1 -1 -1`. There is no sign manipulation anywhere in `BOSSReader.get_charge()`; it's a direct passthrough of whatever BOSS itself prints. And this isn't a QEMU-emulation artifact from local cross-arch testing: it reproduces identically on the live Hugging Face Space, which runs BOSS natively on real x86_64 hardware.

Conclusion: this is a defect (or environment/version issue) in this BOSS 4.9 binary's own AM1SCM1A charge generation for negative net charges, not anything in LigParGen's Python code. There is no data path left on this side to fix — `AM1SP-par`, `AM1SP-cmd`, and the `xZCM1A-`/`xZCM1A+` driver scripts are all BOSS's own proprietary scripts (see ADR-0001), never modified by this repo. The assertion's error message was rewritten to say so plainly (and to stop blaming "the solute may be an open shell," which actively misdiagnosed this specific failure mode) instead of silently degrading behavior or attempting a workaround that isn't actually available from here. Positive net charges are unaffected (`[NH4+]` with `-c 1` computes correctly).

If this needs to move forward, it has to happen upstream, in BOSS itself — worth reporting to whoever maintains the BOSS binary.
