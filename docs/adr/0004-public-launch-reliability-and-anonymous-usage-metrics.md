# Going public: a killable job timeout, an in-memory rate limit, and anonymous-only usage metrics

Moving the Space from Private to Public visibility changes its risk profile: the single-worker queue (`concurrency_limit=1`, chosen for the BOSS-on-32-bit-emulation cost this Space already carries) that was fine for a small trusted group becomes a shared resource anyone can submit to, and "how much is this thing actually used" becomes a real question instead of something we can just ask the handful of people testing it directly.

**Job timeout.** `LigParGen.Converter.convert()` drives BOSS through blocking `os.system()` calls with no timeout of their own — a pathological input hanging BOSS would stall the single-worker queue for every other visitor indefinitely, with no way to recover short of restarting the whole Space. A `signal.alarm`/thread-based timeout can't fix this: Python threads can't be forcibly killed, and terminating just the immediate Python process would orphan BOSS's own child processes (csh scripts, `xZCM1A`, etc.), which would keep running and keep consuming the container's CPU/disk regardless. We run `convert()` in its own forked child process, made a new session/process-group leader via `os.setsid()`, so a timeout can `os.killpg()` the whole tree at once. Verified directly (not just reasoned about): a real BOSS run completes normally within an ample timeout, and a deliberately-too-short timeout on a real run correctly kills it near-immediately with no orphaned subprocess left behind.

**Rate limiting.** In-memory, per-client-IP, sliding window — not backed by any persistent store. This is a real trade-off: the limit resets on every restart/redeploy, and doesn't survive Spaces potentially running behind multiple replicas in the future. Accepted deliberately for v1 because the Space has no other persistent state today (ADR-0003's "no caching across cold starts" already established that posture) and standing up external infra for this alone isn't proportionate yet — a real abuse pattern showing up in usage metrics is the trigger to revisit this, not a guess made now.

**Usage metrics: anonymous job outcomes only, not submitted structures or any request/session identifier.** We push one JSON row per submission (timestamp, input type, atom count, optimization/charge settings, success/failure, error category, duration — never the SMILES/uploaded file itself, never an IP or other visitor identifier) to a private HF Dataset repo via `huggingface_hub`'s `CommitScheduler`, the same runtime-private-repo pattern ADR-0003 already established for the BOSS asset store. The alternative — logging the actual submitted molecules — would tell us more (e.g. what chemistry people are actually running), but is a real privacy/data-retention commitment for a now-public tool that we're deliberately not making without being asked for it directly.
