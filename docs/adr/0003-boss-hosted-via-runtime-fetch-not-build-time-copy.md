# BOSS is fetched at Space container startup, not copied in at build time

The CLI's Dockerfile (ADR-0001) supplies BOSS by `COPY`ing it in from a local, gitignored directory at *build* time — fine for a locally-built image nobody else pulls. The HuggingFace Space needs a different mechanism: Hugging Face builds and stores the image on its own infrastructure, so anything `COPY`'d in at build time becomes part of an image layer that persists on Hugging Face's servers for as long as the Space exists, regardless of the Space's visibility setting.

We considered three options: (a) a self-hosted backend outside Hugging Face entirely, keeping BOSS off Hugging Face's infrastructure completely but requiring the user to stand up and maintain a separate always-on server; (b) a Private-visibility Docker Space that fetches BOSS at container *startup* via an HF Secret from a private BOSS asset store (a private HF Dataset repo), so BOSS lands only in the running container's ephemeral disk, never in a repo or image layer; (c) baking BOSS into the image regardless of visibility, ruled out outright as inconsistent with ADR-0001.

We chose (b): it's the closest hosted equivalent to ADR-0001's "supplied locally, never published" rule that Hugging Face's platform allows, and avoids the operational cost of a separately maintained server. The trade-off, accepted deliberately rather than overlooked: BOSS's bytes do transit and briefly reside on Hugging Face's own infrastructure while the container runs, even though no Hugging Face user other than the Space owner/collaborators can ever reach them. Starting the Space at Private visibility (rather than Public or Protected) was the accompanying call on top of this.
